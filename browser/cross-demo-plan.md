# クロス集計デモ 設計書

readme.md の概要を実装するための詳細設計。現行の `cross-demo.html` / `cross-demo.js`（x, y が 0/1 の 2x2 集計）を、多水準の属性に一般化したものに置き換える。

## 1. 目的とスコープ

she.js（2-level 準同型暗号）を使い、次の 2 種類の集計を暗号化したまま実行するデモを作る。

- クロス集計: 年齢/拠点/出社率/性別のうち 2 個を選び、その分割表（度数）を求める
- 平均: 年齢/拠点/出社率/性別のうち 1 個を選び、その水準ごとの健やか度の平均を求める

デモとしての目的は、クラウドが平文を一切見ずに集計できること、およびアナリストが個票ではなく集計結果しか得られないことを画面上で示すことにある。実運用システムではなく、教育・説明用のデモとして作る。

スコープを次のように限定する。

- ユーザ数の上限は 100 人。これを超える入力は受け付けない
- 不正なユーザの検知（ゼロ知識証明）は実装しない。ユーザは仕様どおりの暗号文を送るものとする。詳細は 10 節

## 2. 前提となる暗号の制約

she は加算が何度でもでき、乗算が 1 回だけできる方式である。この「乗算 1 回」がデモの機能範囲をそのまま決めている。

- 暗号文クラスは CipherTextG1, CipherTextG2, CipherTextGT の 3 種類
- `she.mul(CipherTextG1, CipherTextG2) -> CipherTextGT` が唯一の乗算で、GT になった後はもう掛けられない
- したがって同時に掛け合わせられるのは 2 項まで。3 属性のクロス集計や、条件で絞ってからの集計（フィルタは掛け算 1 回を消費する）はこの方式では実現できない
- readme の仕様「2 属性のクロス集計」「1 属性と健やか度の平均」は、いずれもちょうど乗算 1 回で表現できる範囲になっている

もう一つの制約は復号が離散対数計算を含むことで、復号できる平文の絶対値がテーブルサイズで決まる。詳細は 7 節。

## 4. 暗号化方式へのマッピング

### 4.1 なぜ one-hot にするか

クロス集計のセル度数は、属性 A の水準 i を表す指示関数と属性 B の水準 j を表す指示関数の積の総和である。

```
count[i][j] = Σ_u e^A[u][i] * e^B[u][j]
```

指示関数は 0 か 1 なので、one-hot 表現にしておけば「掛けて足す」だけでセル度数が出る。she は暗号化された 2 つのベクトルの内積が計算できる方式なので、この形がそのまま準同型演算に落ちる。水準番号をそのまま暗号化しても、暗号文のまま「i と等しいか」を判定する手段がないため使えない。

### 4.2 なぜ G1 と G2 の両方で暗号化するか

`she.mul` は G1 と G2 の組にしか適用できない。アナリストがどの 2 属性を選ぶかはユーザがデータを出す時点では分からないので、どの属性が左（G1）になっても右（G2）になっても良いように両方を用意しておく。健やか度も同様に両方持たせる（平均では G2 側だけ使うが、将来の拡張に備える）。

代替案として、アナリストが先にクエリを出し、ユーザが必要な分だけ暗号化するオンライン方式もある。通信量は半分以下になるが、集計のたびに全ユーザがオンラインである必要があり、デモの筋書き（ユーザは一度データを預けて退場する）に合わないので採らない。

### 4.3 掛け算の高速化

`she.mul` は Miller ループと final exponentiation の 2 段からなる。she.js は `she.mulML` と `she.finalExpGT` を JS 側にも公開しており（she-api.md には C++ のみと書かれているが、実際には JS から呼べることを確認した）、次が成り立つ。

```
Σ_u mul(a_u, b_u) = finalExpGT(Σ_u mulML(a_u, b_u))
```

セルごとに final exponentiation を 1 回に減らせるので、ユーザ数が多いほど効く。単体で測ると mul 4.1ms に対し mulML 2.3ms、finalExpGT 1.8ms である。

ただし実装後に測ると、18 セルを回す実際のループの中では mulML が 3.4ms まで落ちる。演算対象が毎回違うオブジェクトになり、1 回ごとに 1536 バイトの GT オブジェクトが生成されるためと思われる（同じ演算対象を 1800 回繰り返す形では 2.3ms のまま変わらないので、反復回数そのものは原因ではない）。したがって削減幅は単体で見たときの 44% ほどではなく、2 割程度と考えておく。

注意点として、`mulML` の結果は final exponentiation 前の中間値であり、そのまま復号したり `pub.encGT(0)` と混ぜたりしてはいけない。累積は mulML 同士の加算だけで行い、最後に一度だけ `finalExpGT` を通す。累積の初期値も `pub.encGT(0)` ではなく最初の mulML 結果を使う（`encGT` は 2.6ms かかるうえ、中間値と混ぜられない）。

## 5. プロトコル詳細

### 5.1 全体の流れ

1. アナリストが `sec.setByCSPRNG()` で秘密鍵を作り、公開鍵 pk を公開する
2. アナリストがクエリ（集計モードと対象属性）をクラウドに伝える
3. 各ユーザが自分の行を one-hot 化し、pk で暗号化してクラウドに送る
4. クラウドが暗号文のまま集計し、集計後の暗号文だけをアナリストに返す
5. アナリストが秘密鍵で復号し、引き算で残りのセルを埋めて表を作る

鍵生成とクエリ指定はどちらもアナリストの作業なので、画面上はアナリストのタブに置き、ユーザとクラウドのタブからは読み取り専用で見えるようにする。

### 5.2 クロス集計

属性 A（水準数 p）と属性 B（水準数 q）を選んだとき、クラウドは次を計算する。

```
cell[i][j] = finalExpGT( Σ_u mulML(u.onehot[A].g1[i], u.onehot[B].g2[j]) )   // CipherTextGT
rowSum[i]  = Σ_u u.onehot[A].g1[i]                                           // CipherTextG1
colSum[j]  = Σ_u u.onehot[B].g2[j]                                           // CipherTextG2
```

ここで cell は全 p*q セルではなく `i < p-1 かつ j < q-1` の範囲だけ計算する。残りは周辺度数からの引き算でアナリストが復元できる。

```
count[i][q-1]   = rowSum[i] - Σ_{j<q-1} count[i][j]                 (i < p-1)
count[p-1][j]   = colSum[j] - Σ_{i<p-1} count[i][j]                 (j < q-1)
count[p-1][q-1] = n - Σ_{i<p-1} rowSum[i] - Σ_{j<q-1} colSum[j] + Σ_{i<p-1, j<q-1} count[i][j]
```

現行デモの `n - x - y + xy` は、この式の p = q = 2 の場合にあたる。

この最適化により、最大ケースである 年齢(7) と 拠点(4) の組でもペアリングは 28 セル分ではなく 18 セル分で済む。復号側も GT 復号（1.8ms）が 18 回、G1/G2 復号（0.1ms）が 11 回で終わる。

さらにアナリスト側では、先に周辺度数を復号して `rowSum[i] == 0` の行と `colSum[j] == 0` の列を見つけ、その行・列の GT 復号を丸ごと省略できる（該当セルは必ず 0）。これはアナリストの復号時間だけを縮める最適化で、クラウドのペアリング回数は減らない。クラウドは rowSum を復号できないので、どの行が空かを知りようがないためである。

### 5.3 平均

属性 A（水準数 p）を選んだとき、クラウドは次を計算する。

```
sumH[i] = finalExpGT( Σ_u mulML(u.onehot[A].g1[i], u.health.g2) )   // CipherTextGT
cnt[i]  = Σ_u u.onehot[A].g1[i]                                     // CipherTextG1
sumAll  = Σ_u u.health.g1                                           // CipherTextG1
```

アナリストは復号後に平文で割る。

```
mean[i] = dec(sumH[i]) / dec(cnt[i])       // cnt[i] == 0 のときは "-" を表示する
overall = dec(sumAll) / n
```

割り算は準同型ではできないので分子と分母を別々に返す。これは仕様上の制約であると同時に、水準ごとの人数がアナリストに見えるということでもある（5.4 参照）。

平均では引き算による省略が実質使えない（`Σ_i sumH[i] = sumAll` が成り立つので 1 水準だけは省けるが、効果が小さいので実装しない）。

### 5.4 小さいセルの扱い

度数 1 のセルや、人数 1 の水準の平均は、その 1 人の値をそのまま露出する。集計であっても個人が特定できるという点はデモで触れる価値があるので、しきい値 k（既定 3）未満のセルを画面上でグレー表示し「* (n < 3)」と出す。ただし抑制しているのはあくまで表示であって、アナリストは復号値そのものを持っている、という点も画面に注記する。

## 6. 計算量とデータ量

以下は Node.js v25（wasm, BN254）での実測値。ブラウザでも同程度になるはずだが、実装後に再測定する。

### 6.1 基本演算

| 演算 | 時間 | 備考 |
| --- | --- | --- |
| `pub.encG1` | 0.165 ms | |
| `pub.encG2` | 0.395 ms | |
| `pub.encGT` | 2.6 ms | 累積の初期値には使わない |
| `ppk.encG1` | 0.058 ms | PrecomputedPublicKey |
| `ppk.encG2` | 0.182 ms | PrecomputedPublicKey |
| `she.mul` | 4.1 ms | |
| `she.mulML` | 2.3 ms | 単体。実際の集計ループの中では 3.4 ms |
| `she.finalExpGT` | 1.8 ms | |
| `she.add` (G1/G2/GT) | 0.004 / 0.008 / 0.020 ms | 無視できる |
| `sec.dec` (G1) | 0.10 ms | |
| `sec.dec` (GT) | 1.6 ms | 平文 10000 まで一定 |
| `sec.isZero` (GT) | 1.6 ms | |

`PrecomputedPublicKey` は encG1 で約 2.8 倍、encG2 で約 2.2 倍速い。ユーザ側は 1 人あたり 36 回暗号化するので必ず使う。使い終わったら `destroy()` を呼ばないとリークする。

### 6.2 暗号文サイズ

| 対象 | バイト数 |
| --- | --- |
| SecretKey | 64 |
| PublicKey | 96 |
| CipherTextG1 | 64 |
| CipherTextG2 | 128 |
| CipherTextGT | 1536 |

1 ユーザあたりの送信量は、one-hot が 17 水準 x (64 + 128) = 3264 バイト、健やか度が 192 バイト、合計 3456 バイト（約 3.4KB）。上限の 100 人で 346KB。

クラウドからアナリストへの返送は、クロス集計（7 x 4）で GT 18 個 27.6KB と周辺度数 約 1KB、平均（7 水準）で GT 7 個 10.8KB と 448 バイト。

### 6.3 想定処理時間

上限いっぱいの n = 100 人での実測値（実装後に測り直したもの）。

| 処理 | 実測 |
| --- | --- |
| ユーザ側の暗号化（100 人分） | 0.78 秒 |
| クラウドのクロス集計 年齢(7) x 拠点(4)、18 セル | 9.1 秒 |
| クラウドのクロス集計 年齢(7) x 性別(3)、12 セル | 5.7 秒 |
| クラウドのクロス集計 性別(3) x 出社率(3)、4 セル | 3.2 秒 |
| クラウドの平均集計 年齢(7 水準) | 3.4 秒 |
| アナリストの復号（18 セル） | 79 ms |

クロス集計の最悪ケースは 年齢 x 拠点 の 9.1 秒で、`3.4ms x 100人 x 18セル` にシリアライズと yield の分が乗ったものである。最適化を入れない場合（`she.mul` を 28 セル分）は 12 秒を超えるので、4.3 節と 5.2 節の 2 つの工夫は効いているが、当初の見積もり 4.6 秒よりは遅い。

セル数が少ない組（3 x 3 で 4 セル）でも 3.2 秒かかっており、セル数に比例しない下駄が 2 秒ほどある。これは 1 ユーザあたり p + q 回の周辺度数の加算と、ユーザレコードの走査のオーバーヘッドによるもの。

ユーザ数の上限が 100 なのでこれが最悪ケースになる。UI がその間固まらないように次を実装する。

- 集計は 60ms の時間予算ごとに `setTimeout(0)` で中断し、進捗バーを更新する。固定個数ではなく時間で区切るのは、1 ステップのコストが暗号化の 8ms から 7x4 集計の 70ms まで開きがあり、かつ入れ子の setTimeout がブラウザで 4ms に丸められるため
- 追加ボタンは 10 人と 30 人にしておき、100 人まではボタンを押した回数で増やさせる
- 余力があれば集計を Web Worker に出す。ただし she のインスタンスと暗号文を worker 側に持たせる必要があるので、暗号文はシリアライズして渡す設計にしてある

## 7. 復号レンジ（DLP）の設定

`she.init(curveType, hashSize, tryNum)` は 8 x hashSize バイトのテーブルを作り、絶対値が `hashSize * tryNum` 以下の平文まで復号できる。範囲を超えると `sheDec` 例外が飛ぶ。

このデモで復号する最大値は健やか度の合計 100n であり、n の上限が 100 なので 10000 である。度数はどれも n 以下なので効いてこない。

実測（平文 10000 を GT 復号）:

| hashSize | tryNum | 復号可能な範囲 | init 時間 | GT 復号 |
| --- | --- | --- | --- | --- |
| 1024 | 16 | 16384 | 0.38 秒 | 1.6 ms |
| 4096 | 4 | 16384 | 0.43 秒 | 1.6 ms |
| 16384 | 1 | 16384 | 0.63 秒 | 1.6 ms |
| 1024 | 1024 | 1048576 | 0.38 秒 | 1.6 ms |

`hashSize = 1024, tryNum = 16` を採用する。テーブルは 8KB、初期化は 0.38 秒で済む。範囲は 16384 なので上限の 100 人でも余裕がある。

同じ範囲でも hashSize を大きくすると init 時間だけが伸びて復号は速くならない。tryNum 側の再試行は 1 回あたりテーブル引きだけで、GT 復号のコストは最初の 1 回のペアリング系演算が支配的なためである。したがってこの規模では小さいテーブルと大きい tryNum の組が有利になる。

ページ読み込み時に初期化している間は status 表示を「初期化中」にしてボタンを無効化する。

`she.loadTableForGTDLP()` で事前計算テーブル（0 から 2^20）を読む手もあるが、9MB 程度のダウンロードが増えるうえ、この範囲では速くならないので採用しない。

## 8. モジュール構成と API

she.js を `<script>` で読む都合上、バンドラは使わずグローバル関数の分割に留める。読み込み順は依存順。

| ファイル | 役割 |
| --- | --- |
| `she.js` | ライブラリ（既存、無変更） |
| `cross-schema.js` | `SCHEMA`, `HEALTH`, one-hot 変換、乱数レコード生成、暗号文の deserialize と `runChunked` の共通処理 |
| `cross-user.js` | ユーザ役。平文レコードの保持と暗号化 |
| `cross-cloud.js` | クラウド役。暗号文の保持と集計 |
| `cross-analyst.js` | アナリスト役。鍵、クエリ、復号、表の復元 |
| `cross-ui.js` | DOM 配線、タブ、テーブル描画、進捗表示 |
| `cross-demo.css` | スタイル（既存を拡張） |
| `cross-demo.html` | 画面（日本語のみ） |

各役は自分の状態をモジュール内の配列に持ち、DOM をデータの置き場にしない。現行の `cross-demo.js` は暗号文を表のセルのテキストとして持ち回り、集計のたびに `deserializeHexStrToCipherTextG1` し直しているが、17 水準 x 100 人の規模ではその方式は破綻するため改める。DOM には表示用の抜粋（先頭 16 文字と省略記号、クリックで全体をコピー）だけを出す。

役の間の「送信」は、送り手が `serialize()` した `Uint8Array` を受け手に渡し、受け手が一度だけ `deserialize()` して保持する形でモデル化する。境界を明示できるうえ、後で Web Worker や実通信に差し替えやすい。

なお `cross-demo.js`（2x2 版の実装）はこの分割で置き換わるので削除した。

主要な関数。

```js
// cross-schema.js

function randomRecord ()                    // -> { age, site, attendance, gender, health }
function runChunked (total, step, onProgress)  // yield every CHUNK_MS, returns a Promise

// cross-user.js
const MAX_USERS = 100

// cross-cloud.js
function cloudReceive (packets)             // deserialize once and store
function cloudCrossTab (keyA, keyB, onProgress)
// -> { cell: CipherTextGT[p-1][q-1], rowSum: CipherTextG1[p], colSum: CipherTextG2[q], n }
function cloudMean (keyA, onProgress)
// -> { sumH: CipherTextGT[p], cnt: CipherTextG1[p], sumAll: CipherTextG1, n }

// cross-analyst.js
function analystInit ()                     // build sec / pub / ppk
function analystSetQuery (mode, keyA, keyB) // mode: 'cross' | 'mean'
function analystDecryptCrossTab (res)       // -> number[p][q] with margins filled in
function analystDecryptMean (res)           // -> { mean: (number|null)[p], cnt: number[p], overall }
```

- 送信後は暗号文の抜粋列を平文テーブルの右に追加し、「クラウドにはこの列しか渡らない」ことを示す

### タブ 2: クラウド（代理秘匿計算）

- 受信件数と、アナリストから指定されたクエリの表示
- 受信した暗号文テーブル（抜粋のみ。平文の列が存在しないことが見て分かるようにする）
- [集計してアナリストに送る] ボタン、進捗バー、所要時間の表示。送信だけを分けても画面に変化がないので 1 個にまとめてある
- 集計結果の暗号文（クロス集計なら (p-1) x (q-1) のセル、平均なら p 個）を抜粋表示。このパネルの見どころなので、送信してもタブは切り替えずここに留まる

### タブ 3: アナリスト（データ解析者）

- 秘密鍵の表示（抜粋）、[鍵を再生成]
- クエリ指定
  - モード: クロス集計 / 平均（ラジオボタン）
  - クロス集計のとき: 属性 A と属性 B のセレクトボックス（同じ属性は選べないようにする）
  - 平均のとき: 属性 A のセレクトボックスのみ（もう一方は健やか度に固定）
  - [クラウドに指示を出す] ボタン
- [結果を受信して復号] ボタン。受信だけを分けても画面に変化がないので 1 個にまとめてある。クラウド側の [アナリストに送る] を押していなくても、このボタンだけで受信から復号まで進む

  - 平均: 水準 | 人数 | 平均健やか度 の表と、全体平均

## 10. 信頼モデルと不正検知

### 10.1 前提

- クラウドは暗号文しか持たない。秘密鍵を持たないので個票も集計値も読めない
- アナリストは秘密鍵を持つが、クラウドからは集計後の暗号文しか受け取らない
- クラウドとアナリストが結託すると個票が復号できる。この方式は両者が結託しないことを前提にしている

この前提は画面上に明記する。デモの見た目では 3 者が同じページに同居しているので、何が誰に見えているのかを言葉で補う必要がある。

### 10.2 不正なユーザについて

ユーザが仕様に反した暗号文（0 でも 1 でもない one-hot 成分、複数の 1、範囲外の健やか度など）を送ると集計値が壊れる。このデモではユーザを正直なものと仮定し、検知は実装しない。デモの主題は秘匿集計そのものであり、証明を入れると画面も処理時間も膨らむためである。

she は対策の手段を一通り持っているので、参考として何ができて何ができないかだけ記しておく。

- one-hot の各成分が 0 か 1 であること、および G1 版と G2 版が同じ値であることは、`pub.encWithZkpBinEq(m)` が返す ZkpBinEq を `pub.verifyZkpBinEq(c1, c2, zkp)` で検証すれば示せる。これはクラウドが秘密鍵なしで実行できる。コストは 1 成分あたり生成 1.8ms・検証 2.6ms、サイズ 224 バイトなので、17 成分では 1 人あたり生成 31ms・検証 44ms、送信量が 3.8KB 増える
- 「1 つの属性の中でちょうど 1 個だけが 1」という制約はクラウドでは検証できない。`Σ_i c_i - Enc(1)` を作ることはできるが、それが 0 かどうかの判定には秘密鍵がいる。アナリストが `sec.isZero()`（GT で 1.6ms）で確認する形になる
- 健やか度が 0 から 100 の範囲にあることの証明手段は she にない。`ZkpSet` は平文が指定した集合に入ることを示せるが、101 要素の集合では証明サイズが大きくなりすぎる

したがって、仮に ZKP を全部入れても健やか度の範囲だけは守れず、不正なユーザは平均値を任意に歪められる。この点も含めて「正直なユーザを仮定する」と画面に明記する。

## 11. 実装ステップ

1. `cross-schema.js` を作り、スキーマと one-hot 変換、乱数レコード生成を書く
2. `cross-demo.html` をタブ 3 枚の骨格に作り替える。まず平文のレコード追加と表示、100 人の上限だけを動かす
3. `cross-user.js` で PrecomputedPublicKey を使った暗号化と、進捗つきのチャンク処理を実装する
4. `cross-cloud.js` でクロス集計（mulML と finalExpGT、引き算前提の (p-1) x (q-1) セル）を実装する
5. `cross-analyst.js` で復号と周辺度数からの復元を実装し、分割表を描く。ここまでで readme の 1 つ目の機能が動く
6. 平均モードを追加する（クラウドとアナリストの両方）
7. `she.init` の hashSize/tryNum を 1024/16 に設定し、100 人での動作と所要時間を確認する
8. 0 の行・列に対する GT 復号スキップと、k 未満セルのグレー表示を入れる
9. ブラウザ（Chrome / Firefox / Safari）で実測し、6 節の見積もりを実測値に差し替える

5 まで終われば demo として成立するので、そこで一度動くものを確認してから先に進む。

## 12. 今後の課題

- 集計の Web Worker 化。数秒間 UI が固まるのはデモとして見栄えが悪い。暗号文をシリアライズして渡す設計にはしてあるので後から入れられる
- ユーザ数の上限を 100 より増やす。クロス集計の時間はユーザ数に比例するので、Web Worker 化とセットで検討する。健やか度の合計が 16384 を超えると DLP の設定も見直しが要る（166 人が境目）
- 不正なユーザの検知（ZkpBinEq による one-hot の検証）。10.2 節に必要な API とコストをまとめてある
- 3 属性以上のクロス集計。2-level 準同型では原理的にできない。実現するには BFV/CKKS のような leveled FHE に載せ替える必要がある
- 条件つき集計（例: 東京に限定した年齢と性別のクロス集計）。フィルタが掛け算を 1 回消費するのでこの方式では不可。ユーザ側で事前に絞る、あるいはフィルタ条件を one-hot に畳み込んだ属性をあらかじめ用意する、といった回避策はある
- 集計結果への差分プライバシ的なノイズ付与。小セル抑制より原理的な保護になるが、デモの主題からは外れる
- ユーザごとの重み付け（例: 回答日時による減衰）。乗算 1 回の枠を使ってしまうので、クロス集計との併用はできない
